# B1 — The Glacier cost gotcha

In the current Terraform lifecycle configuration, sold listing photos are moved to S3 Glacier after 30 days to reduce storage costs.

The problem is that S3 Glacier Flexible Retrieval has a minimum storage duration of 90 days. If an object is deleted before completing those 90 days, AWS applies a prorated early deletion charge for the remaining storage period.

For example:

- Day 0: A property is sold.
- Day 30: Its photos are moved to S3 Glacier.
- Day 40: The seller requests deletion of the photos.

At this point, the photos have spent only 10 days in Glacier. Since the minimum storage duration is 90 days, there are still 80 days remaining.

Even though the application deletes the photos on day 40, AWS charges for the remaining 80 days of the minimum storage period. The exact amount depends on the object size and the AWS region's Glacier storage rate.

This becomes a problem when many sellers request deletion of archived photos. The application may consider the deletion successful, but the AWS bill can still include early deletion charges. These costs can quietly increase without being noticed in the application.

**How I would redesign it**

I would change the lifecycle from a simple time-based archival process into a process that considers the application's deletion and retention requirements.

1. **Check deletion eligibility before archival:** Keep photos in a suitable storage class until the seller's deletion-request window and any required retention period have passed.
2. **Use object tags to control archival:** Apply tags such as `archive_eligible=true` only when an object is ready for long-term storage. Configure the lifecycle rule to transition only eligible objects.
3. **Introduce a deletion workflow:** When a seller requests deletion, check the object's storage class and archival date before deleting it. If an early deletion charge is expected, record the estimated cost and handle it according to the application's retention and deletion policy.
4. **Monitor storage costs:** Use AWS Cost Explorer, cost allocation tags and AWS Budgets to track Glacier storage and early deletion charges. Configure alerts so unexpected costs are identified early.

I would also avoid moving every sold listing photo to Glacier automatically after 30 days. The transition should happen only when the data is genuinely eligible for long-term archival.

**Conclusion:** The main issue is that the current lifecycle considers storage age but does not consider application deletion requests or Glacier's minimum storage duration. By connecting archival eligibility with the application workflow and adding cost monitoring, we can reduce unexpected charges and make storage costs more predictable.
